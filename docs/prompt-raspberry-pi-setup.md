# Prompt: อัปเดตรายงานโครงงาน — ส่วนอุปกรณ์ Raspberry Pi

คัดลอกเนื้อหาด้านล่างทั้งหมดไปวางใน Claude อีกตัวที่ใช้เขียนรายงาน
(ตัวนั้นไม่มีไฟล์โปรเจกต์ในเครื่อง จึงต้องสรุปข้อมูลจริงมาให้ครบในข้อความเดียว)

---

## บริบท

นี่คือโครงงานจบการศึกษา (ปีการศึกษา 2569) ร่วมกับ MTEC: ระบบแจ้งเตือนจุดเสี่ยงอุบัติเหตุ
สำหรับกรุงเทพฯ และปริมณฑล ประกอบด้วย 2 ส่วนหลัก — **เว็บแผนที่** (ทำเสร็จและ deploy แล้ว)
และ **อุปกรณ์ติดรถ (Raspberry Pi)** ที่เพิ่ง setup และทดสอบภาคสนามเสร็จในรอบนี้

ช่วยอัปเดตรายงานโครงงาน (บทที่เกี่ยวกับการพัฒนาระบบ/ผลการทดลอง/ข้อจำกัด) ด้วยข้อมูลด้านล่าง
โดยคงน้ำเสียงและรูปแบบเดิมของรายงานไว้ ไม่ต้องเปลี่ยนโครงสร้างบทใหม่ทั้งหมด

## ภาพรวมสถาปัตยกรรมอุปกรณ์

Raspberry Pi ทำหน้าที่เป็น **อุปกรณ์ติดรถแบบอิสระ** (edge device) ไม่ใช่แค่ตัวรับข้อมูล
— รันเซิร์ฟเวอร์ของตัวเอง อ่าน GPS เอง ตัดสินใจแจ้งเตือนเอง และส่งตำแหน่งขึ้นเว็บให้ดูจากมือถือ

```
ตัวรับ GPS (USB) --NMEA--> pi_alert_client.py --HTTP--> api/server.py (เดียวกับที่เว็บใช้)
                                  |                            |
                                  v                            v
                         ลำโพง (buzzer + เสียงพูด)      หน้าเว็บ (หมุด 🚌 เรียลไทม์)
                                                                |
                                                          ngrok tunnel (โดเมนคงที่)
                                                                |
                                                          มือถือ (bookmark ไว้)
```

**หลักการออกแบบสำคัญ:** อุปกรณ์ต้อง **plug-and-play เต็มรูปแบบ** เพราะตอนใช้งานจริง
ในสนาม/บนรถ ไม่มีคอมพิวเตอร์พกไปด้วย มีแต่โทรศัพท์มือถือ — ทุกอย่างต้องเริ่มทำงานเอง
ตั้งแต่เสียบไฟจนถึงแจ้งเตือน โดยไม่ต้องพิมพ์คำสั่งใด ๆ

## ฮาร์ดแวร์ที่ใช้

| ชิ้นส่วน | รายละเอียด |
|---|---|
| บอร์ดหลัก | Raspberry Pi (รุ่นที่ต้องใช้ไฟเลี้ยง 5V/5A) |
| ตัวรับ GPS | Beltian BE-609U (USB, สื่อสารด้วย NMEA 0183 ผ่านชิป pl2303) |
| ลำโพง | ต่อผ่านการ์ดเสียง USB/HAT (อ้างอิงเป็น `plughw:2,0`) |
| buzzer | ต่อขา GPIO13 (นับแบบ BCM) |
| การเชื่อมต่อเน็ตภาคสนาม | USB LTE dongle (Huawei E3372) |

### รายละเอียดทางเทคนิคที่สำคัญ — ค่า baud rate ของ GPS

ตัวรับ **Beltian BE-609U ตั้งค่าจากโรงงานที่ 115200 baud** ซึ่งผิดจากสมมติฐานเริ่มต้น
(ตัวรับ NMEA ทั่วไปส่วนใหญ่ใช้ 9600 baud) การไล่หาค่านี้เป็นส่วนหนึ่งของกระบวนการ
troubleshoot ฮาร์ดแวร์ที่ใช้เวลานานที่สุดในโครงงาน — วิธีตรวจสอบคือรัน `stty` ตั้งค่า
พอร์ตแล้ว `cat` ดูข้อมูลดิบไล่ทีละค่า (4800/9600/19200/38400/57600/115200) จนกว่าจะเห็น
ประโยค NMEA ที่อ่านออกได้ (ขึ้นต้นด้วย `$GPGGA` หรือ `$GNRMC`)

## ซอฟต์แวร์บนอุปกรณ์

### โมดูลหลัก

**`device/pi_alert_client.py`** — สคริปต์ Python เดียว ไม่พึ่ง dependency ภายนอกนอกจาก
standard library (ตั้งใจออกแบบให้เบา ติดตั้งง่ายบน Pi) ทำหน้าที่:

1. **อ่านพิกัด GPS** — เขียน NMEA parser เอง (ไม่ใช้ pyserial/gpsd) โดยใช้ `stty` ตั้งค่า
   พอร์ตอนุกรมแล้วอ่านไฟล์ตรง ๆ แบบเธรดพื้นหลัง แยกวิเคราะห์ประโยค `GGA` (คุณภาพ fix,
   จำนวนดาวเทียม, พิกัด) และ `RMC` (พิกัด, ความเร็ว) พร้อมตรวจ checksum ทุกบรรทัด
2. **ตรวจจุดเสี่ยงใกล้เคียง** — เรียก API `/api/risk-points/nearby` ทุก 3 วินาที
3. **ตัดสินใจแจ้งเตือน** — มี cooldown ต่อจุด (ไม่พูดซ้ำจนกว่าจะออกนอกรัศมี exit หรือ
   ครบ 5 นาที) และมีการกรองทิศทาง (อธิบายด้านล่าง)
4. **สั่งเสียง** — buzzer (GPIO) + เสียงพูดภาษาไทย ผ่านลำดับชั้นสำรอง 4 ชั้น: ไฟล์เสียง
   Botnoi ที่อัดไว้ล่วงหน้า → Botnoi API สด → Google TTS → espeak-ng (ออฟไลน์)
5. **ส่งตำแหน่งขึ้นเว็บ** — POST พิกัดตัวเองไปที่ `/api/device/location` ทุกรอบ
   ให้หน้าเว็บวาดหมุด 🚌 แบบเรียลไทม์ แยกเป็นคนละหมุดจากตำแหน่งผู้ใช้เว็บเอง

### การกรองทิศทาง (heading-based alert filtering)

ทดลองแล้วว่าการเตือนทุกทิศรอบตัวทำให้เกิดการแจ้งเตือนซ้ำซ้อนไม่จำเป็น (เช่นตอนขับผ่าน
จุดเสี่ยงไปแล้วแต่ยังอยู่ในรัศมี) จึงพัฒนาระบบคำนวณทิศทางที่รถกำลังมุ่งหน้า (bearing)
จากตำแหน่ง GPS สองจุดล่าสุด แล้วเตือนเฉพาะจุดเสี่ยงที่อยู่ในมุม ±90° ด้านหน้า

**ผลการทดลอง (จำลองด้วยเส้นทางจริง):** ลดการเตือนซ้ำซ้อน 41% บนเส้นทางสมุทรสาคร
(รัศมี 500 ม.) และ 9% บนสนามทดสอบ สวทช. (รัศมี 60 ม.) โดยไม่พลาดจุดเสี่ยงจริงจุดใดเลย

**ข้อจำกัดที่ต้องระบุในรายงาน:** การกรองนี้แยกได้แค่ "ข้างหน้า/ข้างหลัง" ไม่สามารถแยก
เลนขาขึ้น-ขาล่องได้ เพราะเลนสวนทางที่อยู่ข้างหน้า 100 เมตร เบี่ยงจากทิศทางรถเพียง ~8.5°
ซึ่งน้อยกว่าความคลาดเคลื่อนของ GPS เอง (5-15 เมตร) — การแยกเลนต้องใช้เทคนิค map matching
กับข้อมูลถนน (เช่น OpenStreetMap) ซึ่งอยู่นอกขอบเขตโครงงานนี้

**สถานะปัจจุบัน (ปิดใช้งานชั่วคราว):** ก่อนออกทดสอบภาคสนามจริงครั้งแรกบนถนน (ชุดข้อมูล
456 คลัสเตอร์ รัศมี 500 ม.) ตัวกรองทิศทางถูกปิดไว้ก่อน (ตั้งเป็น ±180° = ไม่กรอง) เพื่อ
ใช้เป็นเส้นฐานเปรียบเทียบ — เพราะยังไม่เคยมีการทดสอบบนถนนจริงมาก่อน หากเปิดตัวกรองไว้
แล้วระบบไม่แจ้งเตือนตอนที่ควรเตือน จะแยกไม่ออกว่าเป็นเพราะตัวกรองทิศ หรือเพราะปัญหาอื่น
(พิกัด GPS คลาดเคลื่อน/จุดเสี่ยงไม่ครอบคลุม) โค้ดและชุดทดสอบอัตโนมัติ (unit test)
ยังคงอยู่ครบ 29 เคส เปิดกลับได้ทันทีด้วยพารามิเตอร์ไม่ต้องแก้โค้ด

### ระบบเสียงแจ้งสถานะ (เพิ่มเข้ามาหลังพบปัญหาภาคสนาม)

เนื่องจากอุปกรณ์ไม่มีจอแสดงผลตอนใช้งานจริง (ไม่มีคอมพกไปด้วย) จึงออกแบบให้ **ลำโพง
พูดบอกสถานะของตัวระบบเอง** แยกจากเสียงเตือนจุดเสี่ยง:

- ตอนเริ่มทำงาน: "ระบบพร้อมทำงาน กำลังค้นหาสัญญาณดาวเทียม"
- ตอนจับสัญญาณดาวเทียมได้ครั้งแรก: "รับสัญญาณดาวเทียมแล้ว เริ่มแจ้งเตือนจุดเสี่ยง"

เสียงบอกสถานะตั้งความดังไว้ที่ **ครึ่งหนึ่ง** ของเสียงเตือนจุดเสี่ยงเสมอ (ปรับตามสัดส่วน
อัตโนมัติ ไม่ใช่ค่าคงที่) ด้วยเหตุผลเรื่องลำดับความสำคัญ — เสียงเตือนอันตรายต้องดังเด่น
กว่าเสมอ ไม่ให้ผู้ใช้เริ่มชินจนไม่แยกความแตกต่างของเสียงทั้งสองประเภท

### สถานะ "กำลังค้นหาสัญญาณ" บนหน้าเว็บ

หน้าเว็บ (`js/device.js`) แสดงสถานะ 3 แบบแยกจากกันชัดเจน ซึ่งเป็นผลจากการพบปัญหาจริง
ระหว่างทดสอบว่าเดิมทีสองสถานะแรกแยกไม่ออกจากกัน:

| สถานะ | ความหมาย |
|---|---|
| 🔍 กำลังค้นหาสัญญาณดาวเทียม · เห็นดาว N ดวง | อุปกรณ์ทำงานปกติ ยังไม่ได้ตำแหน่ง |
| 🚌 ออนไลน์ | ได้พิกัดแล้ว ทำงานสมบูรณ์ |
| ขาดการเชื่อมต่อ / ไม่เคยส่งตำแหน่ง | เครื่องดับ หรือไม่มีสัญญาณเน็ต |

## การ deploy แบบอัตโนมัติเต็มรูปแบบ (systemd)

ใช้ Linux systemd จัดการ service ทั้งหมด เพื่อให้ระบบเริ่มทำงานเองทันทีที่เสียบไฟ
โดยไม่ต้องมีจอหรือคีย์บอร์ดต่ออยู่:

| Service | หน้าที่ |
|---|---|
| `mtec-api` | รันเซิร์ฟเวอร์ FastAPI (แจกข้อมูลจุดเสี่ยง + รับ/ส่งตำแหน่งอุปกรณ์ + เสิร์ฟหน้าเว็บ) |
| `mtec-alert-client` | ตัวอ่าน GPS และตัดสินใจแจ้งเตือนตามที่อธิบายข้างต้น |
| `mtec-tunnel` | เปิด ngrok tunnel ด้วย **โดเมนคงที่** ให้เข้าถึงจากมือถือได้แม้ไม่ได้อยู่วง WiFi เดียวกัน |
| `mtec-autoheal.timer` | ตรวจทุก 5 นาทีว่า service หลักยังทำงานอยู่ไหม เปิดกลับให้อัตโนมัติถ้าถูกปิดค้างไว้โดยไม่ตั้งใจ |

การใช้ **โดเมนคงที่ของ ngrok** (ไม่ใช่ URL สุ่มที่เปลี่ยนทุกครั้งที่รันใหม่) เป็นการ
ตัดสินใจสำคัญ เพราะทำให้ผู้ใช้ bookmark ลิงก์ไว้ในมือถือได้ครั้งเดียวแล้วใช้ได้ตลอด
โดยไม่ต้องอ่าน URL ใหม่ทุกครั้ง (ซึ่งเป็นไปไม่ได้อยู่แล้วเพราะไม่มีจอตอนใช้งานจริง)

มีสคริปต์ติดตั้งอัตโนมัติ (`scripts/install_services.sh`) และสคริปต์ตรวจสถานะรวม
(`scripts/status.sh`) ที่รายงานสถานะ service ทั้งหมด, ชุดข้อมูลที่โหลดอยู่, พารามิเตอร์
ที่ใช้งานจริง, และสถานะ GPS ในคำสั่งเดียว

## กระบวนการแก้ปัญหาที่พบระหว่างพัฒนา (เหมาะเป็นเนื้อหาบทผลการทดลอง/ข้อจำกัด)

การพัฒนาส่วนอุปกรณ์นี้ให้บทเรียนสำคัญเรื่อง **"อาการเดียวกัน สาเหตุต่างกัน"** ซึ่งเหมาะ
นำไปเขียนในหัวข้อปัญหาที่พบและวิธีแก้ไข:

1. **GPS ไม่ยอมจับสัญญาณเลย** — ไล่สาเหตุตามลำดับ: การเชื่อมต่อ USB หลวม (พบ error
   ระดับโปรโตคอลจากคำสั่ง `dmesg`) → แก้ด้วยการเปลี่ยนพอร์ต USB → พบว่า baud rate เป็น
   ต้นเหตุจริง (9600 ที่คาดไว้ผิด ต้องเป็น 115200) → ยืนยันด้วยการอ่านข้อมูลดิบจากพอร์ต
   อนุกรมโดยตรง

2. **อ่านค่าดาวเทียมได้ "?" ไม่ใช่ตัวเลข** — อาการเดียวกันเป๊ะกับตอน baud rate ผิด
   แต่สาเหตุจริงคือมีสองโปรเซสพยายามอ่านพอร์ตอนุกรมเดียวกันพร้อมกัน (เครื่องมือ
   วินิจฉัยกับ service หลัก) ทำให้ข้อมูลถูกแบ่งอ่านคนละครึ่งจน checksum ไม่ผ่านทั้งคู่
   — แสดงให้เห็นความสำคัญของการแยกวิเคราะห์สาเหตุอย่างเป็นระบบแทนการเดา

3. **เสียเวลาทดสอบภาคสนามเปล่าประโยชน์** — ระบบถูกสั่งหยุดชั่วคราวเพื่อทดสอบเครื่องมือ
   วินิจฉัย แล้วลืมสั่งเปิดกลับก่อนออกทดสอบจริง ทำให้ไม่มีข้อมูลบันทึกเลยตลอดช่วงทดสอบ
   — แก้ปัญหาเชิงระบบด้วยการเพิ่ม `mtec-autoheal.timer` ให้ตรวจสอบและกู้คืนสถานะเอง
   แทนที่จะพึ่งการจดจำของผู้ปฏิบัติงาน

4. **พิกัดผิดเพี้ยนขณะทดสอบในอาคาร** — สังเกตความเร็วที่คำนวณได้สูงผิดปกติ (~85 กม./ชม.
   ขณะอุปกรณ์อยู่นิ่ง) ซึ่งเป็นผลจากปรากฏการณ์ multipath (สัญญาณดาวเทียมสะท้อนผนัง/ตึก
   ก่อนถึงตัวรับ ทำให้คำนวณระยะทางผิด) — เป็นข้อจำกัดโดยธรรมชาติของ GPS ในที่แออัด
   ไม่ใช่บั๊กของซอฟต์แวร์ ยืนยันด้วยการออกไปทดสอบกลางแจ้งแทน

## สิ่งที่ยังต้องทดสอบเพิ่มเติม (ระบุเป็นข้อจำกัด/งานต่อยอด)

- ยังไม่มีการวัดเวลาเฉลี่ยที่ใช้ในการจับสัญญาณดาวเทียมครั้งแรก (cold start) ในสภาพ
  แวดล้อมจริงหลายแบบ (กลางแจ้งเปิด / ใต้สะพาน / ในเมือง)
- ยังไม่มีการทดสอบตัวกรองความคุ้มค่าของพิกัด (เช่น กรองพิกัดที่กระโดดเร็วเกินจริง
  จากปรากฏการณ์ multipath) — เป็นแนวทางพัฒนาต่อที่ระบุไว้แต่ยังไม่ได้ implement
- การกรองทิศทาง ±90° ยังไม่ได้ผ่านการทดสอบกับ GPS จริงบนถนน (ทดสอบด้วยข้อมูลจำลองเท่านั้น)
