# ระบบแจ้งเตือนจุดเสี่ยงอุบัติเหตุ — กรุงเทพฯ และปริมณฑล

เว็บแอปแผนที่ (Leaflet + OpenStreetMap) ติดตามตำแหน่ง GPS แบบเรียลไทม์
เมื่อเข้าใกล้จุดเสี่ยงอุบัติเหตุในระยะ **500 เมตร** จะแจ้งเตือนด้วย**เสียงพูดภาษาไทย**
พร้อมแบนเนอร์บนจอ ระบุสาเหตุความเสี่ยงและคำแนะนำการขับขี่เฉพาะจุด

ข้อมูลจุดเสี่ยงมาจากสถิติอุบัติเหตุปี 2566–2568 (3 ปี) ของ **MOT Data Catalog**
(ไฟล์ `data/accident2025_1.xlsx` รวม **4,627 เหตุการณ์** — 1 ชีตต่อจังหวัด:
กรุงเทพมหานคร นนทบุรี ปทุมธานี สมุทรปราการ นครปฐม สมุทรสาคร)
เหตุการณ์ที่มีพิกัดครบ **13,525 รายการ = จุดเสี่ยง 13,525 จุด** (1 จุดเสี่ยง : 1 อุบัติเหตุ)
นำมาจัดกลุ่มด้วย **DBSCAN สองชั้น (รัศมี 400 ม. ขั้นต่ำ 3 จุด)** — ชั้นแรกทั้งพื้นที่
ชั้นสองแยกตามสายทาง — ได้ **คลัสเตอร์ 456 วง** อีก 1,508 จุดไม่เกาะกลุ่มกับจุดใด
จึงไม่เข้านิยาม Black Spot และ**ไม่นำมาจัดระดับ** จัดระดับเฉพาะ 456 คลัสเตอร์
ด้วย**โมเดล v3**:
**Severity Index** `SI = (F + PI) / Total Accident` →
แบ่ง 3 ระดับที่ SI < 1 / 1–2 / ≥ 2 (🔴 สูง 5 · 🟠 ปานกลาง 47 · 🟢 ต่ำ 140 วง)

## คำศัพท์ที่ต้องแยกให้ชัด

เอกสารและโค้ดทั้งหมดในโปรเจกต์นี้ใช้สามคำนี้ต่างกัน ห้ามใช้สลับกัน

| คำ | นิยาม | จำนวน (รอบ v2569-r1-3y) | อยู่ในไฟล์ |
|---|---|---|---|
| **จุดเสี่ยง** | **1 จุด : 1 อุบัติเหตุ** — เหตุการณ์รายครั้งที่มีพิกัด | **13,525 จุด** | `data/accident_points_3y.geojson` |
| **คลัสเตอร์** | วงที่ DBSCAN รวมจุดเสี่ยงตั้งแต่ 3 จุดขึ้นไปเข้าด้วยกัน **บนสายทางเดียวกัน** | **456 วง** | `data/risk_points_bkk_metro_3y.geojson` (`unit_type: cluster`) |
| **หน่วยวิเคราะห์** | = คลัสเตอร์เท่านั้น (ตั้งแต่ r9) เป็นหน่วยที่คำนวณ SI และจัดระดับ | **456 วง** | ไฟล์เดียวกับคลัสเตอร์ |

บนแผนที่แสดง **คลัสเตอร์ 456 วง** เป็นหมุดกลมสีตามระดับ และมี**ชั้นดูจุดเสี่ยง
รายอุบัติเหตุ 13,525 จุด** (`js/accidents.js`) เป็นเลเยอร์เสริมที่ติ๊กเปิด/ปิดได้
ในแผงตัวกรอง เริ่มต้นปิดไว้

**โหมดตรวจสอบคลัสเตอร์** — กดที่หมุดคลัสเตอร์ใดก็ได้ ระบบจะวาด **ขอบเขตจริง
(convex hull)** ของกลุ่มพร้อม **จุดเสี่ยงสมาชิกทุกจุด** ทับลงไป ปิดป๊อปอัปแล้วหายไป
ใช้ยืนยันด้วยตาว่า DBSCAN จัดกลุ่มจุดไหนเข้าวงไหนจริง ๆ ตรวจได้ว่าจำนวนจุดที่เห็น
ตรงกับ `accident_count` ในป๊อปอัป (ตรวจแล้วจับคู่ครบ 456/456 คลัสเตอร์)

ใช้ convex hull แทนวงกลมเพราะวงกลมจะซ่อนรูปร่างจริงของกลุ่มที่ยืดยาวตามถนน
(chaining) — ขอบเขตจริงทำให้เห็นปัญหานี้ทันทีแทนที่จะกลบไว้

การแจ้งเตือนตรวจกับ **คลัสเตอร์ทั้ง 456 วง** ไม่ใช่จุดเสี่ยงรายอุบัติเหตุ
เพราะถ้าเตือนทีละอุบัติเหตุจะเตือนซ้ำหลายสิบครั้งในคลัสเตอร์เดียว
**ชั้นดูจุดเสี่ยง 13,525 จุดไม่เกี่ยวกับการแจ้งเตือนเลย** เปิดหรือปิดก็ไม่ทำให้
เสียงเตือนเปลี่ยน เพราะ `alert.js` อ่านจาก `RiskPoints.visible()` ซึ่งเป็นคลัสเตอร์ล้วน

> ⚠️ **จุดเสี่ยงเดี่ยว 1,508 จุดไม่ถูกจัดระดับ** เพราะไม่เข้านิยาม Black Spot ที่ต้อง
> เกิดซ้ำอย่างน้อย 3 ครั้ง แต่ยังนับอยู่ใน**สถิติภาพรวม** (`calibration.overall`)
> เพื่อไม่ให้ผู้เสียชีวิต 114 คนและ EPDO 967.58 ลบ. ของจุดเหล่านี้หายไปจากข้อสรุป

## DBSCAN: หลักการรวมจุดเสี่ยงให้เป็น "คลัสเตอร์"

พิกัด GPS ของเหตุที่เกิด "บริเวณเดียวกัน" ในโลกจริงไม่ตรงกันเป๊ะ จึงต้องรวมจุดเสี่ยง
ที่เกิดใกล้กันเป็นคลัสเตอร์ก่อนคำนวณระดับ — ใช้ **DBSCAN**
(Density-Based Spatial Clustering of Applications with Noise) ซึ่งมองหา
"บริเวณที่จุดหนาแน่น" ด้วยพารามิเตอร์ 2 ตัว:

- **eps (ε)** — รัศมีเพื่อนบ้าน ที่นี่ใช้ **400 เมตร** (ระยะ haversine บนผิวโลก)
- **min_samples** — จำนวนจุดเสี่ยงขั้นต่ำในรัศมี ที่นี่ใช้ **3**

**รันสองชั้น** (ตั้งแต่ r10) — ชั้นแรกทั้งพื้นที่ ชั้นสองแยกสมาชิกของแต่ละกลุ่ม
ตาม**สายทาง** แล้วรัน DBSCAN ซ้ำในแต่ละสายทาง ทำให้ทุกคลัสเตอร์อยู่บนสายทางเดียว

ที่มาของ 400 เมตร: ค่ามัธยฐานระยะห่างเพื่อนบ้านลำดับที่ 3 ของข้อมูลจริงคือ **97.08 เมตร**
แล้วปรับกว้างขึ้นตามตำแหน่งจุดข้อศอกของ sorted k-distance graph (Ester et al. 1996)
ซึ่งเป็นการตีความด้วยสายตา ไม่ใช่สูตรที่ให้ผลเดียวแน่นอน — เลือก 400 ม. เพื่อให้
หน่วยวิเคราะห์ครอบคลุมช่วงถนนหนึ่งช่วง คือระดับช่วงทาง ไม่ใช่รายจุด

อัลกอริทึมจำแนกทุกเหตุการณ์เป็น 3 ประเภท:

| ประเภท | เงื่อนไข | ผลต่อระบบ |
|---|---|---|
| **Core point** | มีเพื่อนบ้าน ≥ 3 จุดเสี่ยงในรัศมี 400 ม. | เป็นแกนของคลัสเตอร์ และ "ลาม" ต่อไปยัง core อื่นที่อยู่ในรัศมีกันได้ (chain) |
| **Border point** | อยู่ในรัศมีของ core แต่เพื่อนบ้านตัวเองไม่ถึง 3 | ถูกนับรวมเข้าคลัสเตอร์ข้างเคียง |
| **Noise** | ไม่เข้าเงื่อนไขทั้งสอง | เหตุกระจัดกระจาย ไม่เข้าคลัสเตอร์ใด **ไม่นำมาจัดระดับ** แต่ยังนับในสถิติภาพรวม (รอบนี้ 1,508 จาก 13,525 จุดเสี่ยง) |

> ⚠️ **chaining** — การ "ลาม" ของ core point ทำให้กลุ่มยืดยาวไปตามถนนได้ไม่จำกัด
> การรันชั้นที่สองแยกตามสายทางตัดปัญหา chaining **ข้ามถนน** ได้หมด (จากเดิมมีวง
> ที่คร่อมถึง 11 สายทาง เหลือ 0 วง) แต่ถนนสายเดียวที่ยาวมากยังลามเป็นโซ่ได้
> คลัสเตอร์ใหญ่ที่สุดคือ **922 จุดเสี่ยง รัศมี 7.9 กม.** (ถนนสายเดียวกับรอบ 1 ปี
> ที่มี 712 จุด — จำนวนจุดเพิ่มตามข้อมูล 3 ปี แต่รัศมีไม่โตขึ้น)
> วงขนาดนี้ควรตีความเป็นช่วงสายทาง ไม่ใช่จุดเฉพาะเจาะจง

เหตุผลที่ DBSCAN เหมาะกับงาน accident hotspot กว่าวิธีอื่น (เช่น K-Means):

1. **ไม่ต้องกำหนดจำนวนกลุ่มล่วงหน้า** — เราไม่มีทางรู้ก่อนว่ากรุงเทพฯ มีจุดเสี่ยงกี่จุด
2. **จับกลุ่มรูปทรงอิสระได้** — อุบัติเหตุเรียงตัวเป็นแนวยาวตามถนน/ทางโค้ง ไม่ใช่วงกลม
3. **แยก noise ออกเองโดยธรรมชาติ** — เหตุการณ์เดี่ยวๆ ที่เกิดกระจัดกระจายไม่ถูกบังคับ
   ให้เข้ากลุ่มใดกลุ่มหนึ่ง (K-Means บังคับทุกจุดเข้ากลุ่ม ทำให้ centroid เพี้ยน)
4. **ขั้นต่ำ 3 เหตุการณ์** สอดคล้องนิยาม Black Spot มาตรฐานออสเตรเลีย
   (อุบัติเหตุบาดเจ็บ/เสียชีวิต ≥ 3 ครั้งในช่วงเวลาที่กำหนด)

ผลลัพธ์: จุดเสี่ยง **13,525 จุด** → **456 คลัสเตอร์** (ครอบคลุมจุดเสี่ยง 12,017 จุด
คิดเป็น 88.9%) + จุดเสี่ยงเดี่ยว **1,508 จุด** ที่ไม่นำมาจัดระดับ
**ตำแหน่งหมุดของคลัสเตอร์ = medoid** คือจุดอุบัติเหตุจริงที่อยู่ใกล้จุดกึ่งกลางที่สุด
ไม่ใช่จุดกึ่งกลางเลขคณิต (centroid) — เพราะเมื่อกลุ่มทอดยาวตามถนนที่โค้ง ค่าเฉลี่ย
ของพิกัดจะตกลงไปในช่องว่างในเส้นโค้ง ซึ่งไม่ใช่ตำแหน่งบนถนน (เหมือนหาจุดกึ่งกลาง
ของเกือกม้าแล้วได้จุดที่ลอยกลางอากาศ) ใช้ medoid แล้ว **หมุดอยู่บนถนนเสมอ**
เพราะเป็นตำแหน่งอุบัติเหตุจริง — ตรวจแล้วทั้ง 456 วงมีระยะจากหมุดถึงจุดอุบัติเหตุ
ที่ใกล้ที่สุดเท่ากับ 0 เมตร

สถิติทุกตัว (ผู้เสียชีวิต มูลค่าความเสียหาย ฯลฯ) รวมจากสมาชิกทั้งหมดของกลุ่ม ·
GeoJSON มีฟิลด์ `unit_type` (`cluster` / `noise`), `radius_m` = ระยะจากหมุดถึงสมาชิก
ที่ไกลที่สุด และ `centroid` = จุดกึ่งกลางเลขคณิตเก็บไว้ตรวจย้อนหลัง

### ชื่อสายทางที่ต้นทางไม่ได้กรอกมา

ข้อมูลต้นทางเว้นคอลัมน์ "สายทาง" ไว้จำนวนไม่น้อย (ชุด 3 ปี 2566-2568: 3,938 จาก
13,525 แถว) ทั้งที่แถวเดียวกันกรอก "รหัสสายทาง" กับ "KM" มาครบ คลัสเตอร์ที่สมาชิก
เป็นแถวแบบนี้ทั้งวงจึงเคยขึ้นหัวป๊อปอัปว่า **ไม่ระบุ** — ชุด 3 ปีมี 106 จาก 456 วง

สคริปต์จึงเติมชื่อให้ด้วยการ **ยืมชื่อจากจุดที่ใกล้ที่สุดซึ่งอยู่บนรหัสสายทางเดียวกัน
และมีชื่อกรอกไว้** ในชุดข้อมูลเดียวกัน (เพดาน 2 กม. — ไกลกว่านั้นถือว่าคนละตอนของ
สายทาง เลิกเดาชื่อแล้วใช้ "รหัสสายทาง + หลัก กม." เช่น `ทล.3481 กม.1-1.4` แทน)
ที่ไม่ใช้ฐานนิยมของรหัสสายทางเพราะหนึ่งรหัสมีหลายตอนคนละชื่อ (ทล.9 มีทั้ง
"บางปะอิน - แขวงรามอินทรา" และ "แขวงรามอินทรา - บางพลี") จะติดชื่อผิดครึ่งสายทาง

ผลชุด 3 ปี: 106 วง → ยืมชื่อได้ 104 วง (ระยะถึงจุดอ้างอิงมัธยฐาน 63 ม.) ·
ใช้รหัสสายทาง 2 วง · เหลือ "ไม่ระบุ" 0 วง

ข้อควรระวังในการอ้างอิง: ชื่อที่เติมเป็น **ค่าอนุมาน** ไม่ใช่ค่าที่ต้นทางกรอก
GeoJSON จึงเก็บแยกกัน — `road` = ค่าดิบที่ใช้จัดกลุ่ม (ยังเป็น `ไม่ระบุ` ตามเดิม),
`road_label` = ชื่อสำหรับแสดงผล, `road_label_source` = ที่มา (`record` /
`nearest_road` / `route_ref` / `unknown`), `road_ref` = ป้ายอ้างอิง `ทล.9 กม.9.2-35.4`
หน้าเว็บแสดงชื่อที่อนุมานด้วยเครื่องหมาย `≈` นำหน้าเสมอ

การเติมชื่อทำ **หลัง** จัดกลุ่มเสร็จแล้ว (`fill_road_labels`) จึงไม่กระทบจำนวน
คลัสเตอร์ ค่า SI หรือระดับความเสี่ยง — ตรวจกับผลรอบก่อนแล้วว่าฟิลด์เดิมทุกตัว
ของทั้ง 456 วงมีค่าเท่าเดิมทุกค่า

## Severity Index โมเดล v3 (ดัชนีความรุนแรงอุบัติเหตุ)

แต่ละ**หน่วยวิเคราะห์**จัดระดับด้วยสูตรเดียว ไม่มีการถ่วงน้ำหนักหลายเกณฑ์
(จุดเสี่ยงรายอุบัติเหตุรับระดับมาจากหน่วยที่ตัวเองสังกัด ไม่ได้คำนวณ SI แยกรายจุด)

```
SI = (F + PI) / Total Accident
```

| สัญลักษณ์ | ความหมาย | หน่วย |
|---|---|---|
| `F` | จำนวนอุบัติเหตุที่ก่อให้เกิดการสูญเสียชีวิตในหน่วยนั้น | **ครั้ง** (ไม่ใช่จำนวนศพ) |
| `PI` | จำนวนผู้บาดเจ็บรวม (สาหัส + เล็กน้อย) | **คน** |
| `Total Accident` | จำนวนจุดเสี่ยงทั้งหมดในหน่วยนั้น | ครั้ง |

ที่มาของสูตร: วิทยานิพนธ์ของ **ณัฐพงศ์ ซื่อสัตย์ (2558)** ใช้ตามต้นฉบับไม่ดัดแปลง

**แบ่ง 3 ระดับด้วยจุดตัดคงที่:** 🟢 ต่ำ SI < 1 · 🟠 ปานกลาง 1 ≤ SI < 2 · 🔴 สูง SI ≥ 2
(จุดตัดตรงกับ "ที่ราบ" ของการกระจาย SI — รอบ 3 ปีที่ P71–P80 ให้ SI = 1.000 เท่ากันยาว
และเสถียรกว่าเกณฑ์เปอร์เซ็นไทล์เมื่อข้อมูลเพิ่ม ดู `docs/risk-score-criteria.md` หัวข้อ 4)

รายงานคู่กับ **EPDO** ซึ่งเป็นตัวชี้วัดอิสระ ไม่ผสมลงในการจัดระดับ

```
EPDO = 6.7F + 2.0S + 0.058M   (ล้านบาท; F/S/M นับเป็นจำนวน "คน")
```

น้ำหนักคือต้นทุนความสูญเสียต่อรายของ TDRI ปีงบประมาณ 2565 ในหน่วยล้านบาท
EPDO รวมทุกจุดเสี่ยง = **6,285.24 ล้านบาท** (ไม่เปลี่ยนตามวิธีจัดกลุ่ม)
เฉพาะส่วนที่อยู่ใน 456 คลัสเตอร์ = **3,637.16 ล้านบาท** · จุดเสี่ยงเดี่ยว = 2,648.08 ลบ.

> ⚠️ **SI กับ EPDO ตอบคนละคำถาม** SI คือความรุนแรงเฉลี่ยต่อครั้ง EPDO คือความสูญเสียรวม
> คลัสเตอร์ที่เกิดเหตุถี่สุด (922 จุดเสี่ยง) ได้ SI เพียง 0.68 จัดเป็นระดับต่ำ และ
> คลัสเตอร์ที่มี EPDO สูงสุดในชุดข้อมูล (208.55 ลบ.) ก็เป็นระดับต่ำเช่นกัน
> — ต้องรายงานทั้งสองค่าคู่กันเสมอ

> **ประวัติ:** v1 log-norm 30/35/20/15 → v2 (r1–r6) คะแนน 4 เกณฑ์ × 25% เต็ม 100
> → v3 (r7) SI ที่ eps 200 ม. → r8 กลับมา eps 400 ม. → r9 ตัดจุดเสี่ยงเดี่ยวออกจาก
> การจัดระดับ → r10 DBSCAN สองชั้น แยกคลัสเตอร์ตามสายทาง → r11 ปักหมุดหลายจุด
> ต่อคลัสเตอร์ (ย้อนกลับเพราะแผนที่รก) → **r12 ย้ายหมุดจาก centroid เป็น medoid**
> โค้ดและ snapshot ของ v1/v2 ยังอยู่ใน git history และ `data/calibrations/v2568-r1..r5`

**Fixed-Schedule Recalibration (หลักการสำคัญที่สุด):** ผลทั้งหมดคำนวณแล้ว "ล็อก"
เป็นเวอร์ชัน (`data/calibrations/v2568-r12.json`) — **ไม่คำนวณใหม่ทุกครั้งที่เปิดแอป**
ไม่งั้นคะแนนจุดเดิมจะลอยขึ้นลงเมื่อมีเหตุใหม่เข้าระบบแม้เหตุเดียว เปรียบเทียบข้ามเวลาไม่ได้
กำหนดรอบคำนวณใหม่ล่วงหน้า **ทุก 6 เดือน** (แนวทาง NCDOT/UNC HSRC 2011)
หน้าเว็บ (เรียลไทม์) แค่อ่านผลที่คำนวณไว้แล้ว — ท้ายหน้าแดชบอร์ดระบุเวอร์ชันรอบคำนวณกำกับไว้

รายละเอียดสูตรทุกเกณฑ์ + เหตุผลการเลือกวิธี + อ้างอิงครบ: **[docs/risk-score-criteria.md](docs/risk-score-criteria.md)**

## REST API สำหรับอุปกรณ์ (`api/server.py`)

เซิร์ฟเวอร์ FastAPI แจกจ่ายข้อมูลจุดเสี่ยงให้อุปกรณ์ภายนอก (Raspberry Pi, มือถือ ฯลฯ)
และเสิร์ฟหน้าเว็บเดิมไปพร้อมกัน — ใช้เซิร์ฟเวอร์เดียวแทน `py -m http.server` ได้เลย

| Endpoint | ใช้ทำอะไร |
|---|---|
| `GET /api/health` | ตรวจว่าแจกข้อมูลชุดไหน รอบคำนวณอะไร |
| `GET /api/risk-points` | จุดเสี่ยงทั้งหมด (กรอง level / province / min_si ได้) |
| `GET /api/risk-points/nearby` | จุดเสี่ยงในรัศมี + `alert_message` ให้อุปกรณ์พูดได้ทันที |
| `GET /api/risk-points/{id}` | รายละเอียดจุดเดียว |
| `POST /api/device/location` | Pi ส่งพิกัด GPS ปัจจุบันของตัวเองขึ้นมา |
| `GET /api/device/location` | เว็บดึงพิกัดล่าสุดของ Pi ไปวาดหมุดเรียลไทม์ |
| `GET /api/tts` | ตัวกลางเรียก Botnoi Voice (ซ่อน token + cache) |

```bash
pip install -r api/requirements.txt
python -m uvicorn api.server:app --host 0.0.0.0 --port 8000
# เว็บ:      http://localhost:8000
# API docs:  http://localhost:8000/docs   (Swagger UI อัตโนมัติ)
```

### รันแบบไม่ต้องเปิดหน้าจอ/เทอร์มินัลค้างไว้ (systemd)

คำสั่งข้างบนต้องมีเทอร์มินัลเปิดค้างตลอด ปิดหน้าต่างหรือปิด SSH เมื่อไหร่โปรแกรมก็หยุด
ถ้าจะติดตั้งใช้งานจริงบนรถ (ไม่มีจอ ไม่มีคนเปิดเทอร์มินัลให้) ให้ตั้งเป็น **systemd service**
แทน — เริ่มทำงานเองตอนเปิดเครื่อง รันอยู่เบื้องหลังตลอด และรีสตาร์ทเองถ้าโปรแกรมพัง

ไฟล์ตั้งต้นอยู่ที่ `systemd/mtec-api.service` (เซิร์ฟเวอร์) และ
`systemd/mtec-alert-client.service` (ไคลเอนต์บนอุปกรณ์ ใช้กับ GPS จริง ไม่ใช่โหมด `--route`)

```bash
cd ~/mtec-risk-alert-system

# คัดลอกไฟล์ตั้งค่าเข้าระบบ (ทำครั้งเดียว)
sudo cp systemd/mtec-api.service /etc/systemd/system/
sudo cp systemd/mtec-alert-client.service /etc/systemd/system/

# ถ้า user ไม่ใช่ pi หรือโฟลเดอร์โปรเจกต์อยู่คนละที่ ให้แก้ User=/WorkingDirectory
# ในไฟล์ /etc/systemd/system/*.service ก่อนขั้นตอนถัดไป
sudo nano /etc/systemd/system/mtec-alert-client.service   # เช็ค --audio-device ให้ตรงเลขการ์ด

sudo systemctl daemon-reload
sudo systemctl enable --now mtec-api.service
sudo systemctl enable --now mtec-alert-client.service
```

`enable --now` สั่งสองอย่างพร้อมกัน: เริ่มทำงานทันที และให้เริ่มเองทุกครั้งที่ Pi บูต
หลังจากนี้**ปิดหน้าจอ ถอด SSH หรือปิด-เปิดเครื่องใหม่ได้เลย ระบบทำงานต่อเนื่อง**

คำสั่งที่ใช้บ่อยหลังตั้งเป็น service แล้ว:

```bash
sudo systemctl status mtec-api.service           # เช็คว่ากำลังรันอยู่ไหม
sudo journalctl -u mtec-api.service -f            # ดู log สด (Ctrl+C ออก)
sudo journalctl -u mtec-alert-client.service -f   # log ของไคลเอนต์ เห็นบรรทัด [ALERT]/[เสียง]
sudo systemctl restart mtec-api.service           # รีสตาร์ท เช่นหลัง build ข้อมูลใหม่
sudo systemctl stop mtec-alert-client.service      # หยุดชั่วคราว
sudo systemctl disable mtec-api.service           # เลิกให้เริ่มเองตอนบูต (ยังรันอยู่จนกว่าจะ stop)
```

⚠️ `mtec-alert-client.service` ตั้งค่าไว้ให้ใช้ `--gpsd` (โหมด GPS จริง) เพราะเป็นค่าที่เหมาะกับ
การติดตั้งถาวรบนรถ ถ้าจะทดสอบด้วยเส้นทางจำลองให้รันคำสั่งมือแบบเดิมแทน ไม่ต้องผ่าน service
(ปกติจะมี `mtec-alert-client.service` รันเงียบ ๆ อยู่แล้ว ให้ `sudo systemctl stop
mtec-alert-client.service` ก่อน ไม่งั้นจะมีสองโปรเซสแย่งกันคุยกับ GPIO เดียวกัน)

| Endpoint | ความหมาย |
|---|---|
| `GET /api/health` | สถานะเซิร์ฟเวอร์ + จำนวนจุดเสี่ยง |
| `GET /api/risk-points` | ทุกจุด กรองได้: `?level=high` `?province=นนทบุรี` `?min_si=1.5` |
| `GET /api/risk-points/nearby?lat=..&lng=..&radius=600` | จุดในรัศมี เรียงใกล้→ไกล พร้อม `distance_m` และ **`alert_message`** (ข้อความเตือนไทยสำเร็จรูป สร้างจากกติกา Dynamic Alert เดียวกับเว็บ) |
| `GET /api/risk-points/{id}` | รายละเอียดจุดเดียว + ปัจจัยเสี่ยง |

`GET /api/health` บอกชื่อไฟล์ + เวอร์ชันรอบคำนวณที่กำลังใช้อยู่ ใช้ตรวจหลัง build ข้อมูลใหม่ได้

## ไคลเอนต์ Raspberry Pi (`device/pi_alert_client.py`)

ภาษาไทย** ที่ได้จากฟิลด์ `alert_message` ของ API
ใช้กติกา cooldown ชุดเดียวกับหน้าเว็บ ใช้เฉพาะ Python standard library ไม่ต้อง pip install

### ต่อตัวรับ GPS Beltian BE-609U (USB)

ตัวรับ GPS ที่ใช้จริงในโปรเจกต์นี้ **เสียบพอร์ต USB ของ Pi ช่องไหนก็ได้ ไม่ต้องต่อสายขา GPIO**
(คนละเรื่องกับ MAX98357A ที่ต้องต่อสาย 5 เส้น) มันคุยด้วยโปรโตคอลมาตรฐาน **NMEA 0183**
ผ่าน serial ซึ่ง Linux มองเห็นเป็นไฟล์พอร์ตอันหนึ่ง

```bash
# 1. เสียบ USB แล้วดูว่าระบบเห็นไหม
ls -l /dev/serial/by-id/     # ชื่อคงที่ ไม่สลับเลขเวลาเสียบ USB อื่นเพิ่ม — โค้ดหาอันนี้ก่อน
ls -l /dev/ttyACM* /dev/ttyUSB*
lsusb                        # ถ้าไม่เห็นไฟล์พอร์ตเลย ดูว่าตัวอุปกรณ์โผล่ใน lsusb ไหม

# 2. ให้สิทธิ์อ่านพอร์ต (ครั้งเดียว แล้ว logout/login หรือ reboot)
sudo usermod -a -G dialout $USER

# 3. ตรวจว่าตัวรับทำงานและจับดาวได้กี่ดวง (โหมดนี้ไม่ยิง API เลย)
python3 device/pi_alert_client.py --checkgps
```

`--checkgps` จะฟัง NMEA 20 วินาทีแล้วรายงานทีละวินาทีว่าได้พิกัดหรือยัง เห็นดาวกี่ดวง
ถ้าได้พิกัดจะพิมพ์ลิงก์ Google Maps ให้กดเทียบว่าตรงกับที่ยืนอยู่จริงไหม

**ตัวรับที่เพิ่งเปิดเครื่องต้องใช้เวลาจับดาวครั้งแรก 30 วินาที – 2 นาที และต้องอยู่กลางแจ้ง
หรือริมหน้าต่าง** — ในอาคารลึก ๆ จับดาวไม่ได้เลย ไม่ใช่อุปกรณ์เสีย นี่เป็นสาเหตุอันดับหนึ่ง
ที่ `--serial` แล้วขึ้น "ยังไม่ได้ตำแหน่ง (รอสัญญาณดาวเทียม)" ค้างอยู่

| อาการ | สาเหตุที่พบบ่อย | วิธีแก้ |
|---|---|---|
| หาพอร์ตไม่เจอ | ยังไม่เสียบ / สาย USB เป็นสายชาร์จอย่างเดียว | เปลี่ยนสาย ดู `lsusb` |
| `Permission denied` | ผู้ใช้ยังไม่อยู่กลุ่ม `dialout` | `sudo usermod -a -G dialout $USER` แล้ว reboot |
| เปิดพอร์ตไม่ได้ (ถูกจับจอง) | มี `gpsd` ติดตั้งไว้และยึดพอร์ตไปแล้ว | `sudo systemctl stop gpsd gpsd.socket` |
| เห็นดาวแต่ไม่ได้พิกัด | ดาวยังไม่พอ (ต้องอย่างน้อย 4 ดวง) | ออกกลางแจ้ง รออีก 1–2 นาที |
| ไม่มีข้อมูลเข้ามาเลย | พอร์ตผิดตัว หรือ baud ไม่ใช่ 9600 | `--checkgps /dev/ttyUSB0` · ดูดิบ ๆ ด้วย `cat /dev/ttyACM0` |

**ทำไมไม่ใช้ `gpsd`:** `--serial` อ่าน NMEA ตรงจากพอร์ต ไม่ต้องติดตั้งหรือคอยตั้งค่า service
เพิ่มอีกตัว และไม่ต้องใช้ไลบรารีนอก standard library เลย (`pyserial` ก็ไม่ต้อง — บน Linux
พอร์ต serial เปิดเป็นไฟล์ธรรมดาได้ ส่วน baud rate ยืมคำสั่ง `stty` ของระบบ)
โหมด `--gpsd` ยังใช้ได้อยู่ถ้าติดตั้ง gpsd ไว้แล้ว แต่ไม่ใช่ทางหลักอีกต่อไป

โค้ดอ่านทั้งประโยค `GGA` (พิกัด + จำนวนดาว + คุณภาพ fix) และ `RMC` (พิกัด + ความเร็ว)
รองรับทั้ง `$GP` (GPS อย่างเดียว) และ `$GN` (หลายระบบดาวเทียมรวมกัน) ตรวจ checksum
ทุกบรรทัด และ**ทิ้งพิกัดที่ fix quality = 0** เพราะบรรทัดแบบนั้นมักมีพิกัด `0,0`
ซึ่งจะทำให้หมุดกระโดดไปโผล่กลางมหาสมุทรแอตแลนติก

### ดูตำแหน่งรถแบบเรียลไทม์จากมือถือ

ทุกครั้งที่ไคลเอนต์อ่านพิกัดได้ มันจะส่งขึ้น `POST /api/device/location` ด้วย
หน้าเว็บ (`js/device.js`) ดึงกลับมาทุก 2 วินาทีแล้ววาดเป็นหมุด 🚌 บนแผนที่
**เปิดจากมือถือเครื่องไหนก็ได้ที่อยู่วงแลนเดียวกัน โดยไม่ต้องนั่งอยู่บนรถคันนั้น**

```
Pi (GPS BE-609U) --POST--> /api/device/location --GET--> เว็บบนมือถือ --> หมุด 🚌
```

ใช้ได้กับแผนที่ทั้งสามโหมดโดยไม่ต้องตั้งค่าอะไรเพิ่ม เพราะเป็นชั้นข้อมูลอิสระ
ไม่ยุ่งกับ `GPS.start()` หรือระบบเตือนของเว็บ:

| หน้า | เห็นหมุด 🚌 ของ Pi | หมายเหตุ |
|---|---|---|
| `index.html` (แผนที่จริง) | ✅ | ใช้ตอนขับจริง |
| `index.html?mock=1` (จำลอง) | ✅ | หมุดน้ำเงินวิ่งตามเส้นทางจำลองของเว็บ ส่วน 🚌 คือตำแหน่ง Pi จริง — เห็นพร้อมกันได้ |
| `test-nstda.html` (สนาม สวทช.) | ✅ | ใช้ตอนทดสอบขับวนรอบอุทยานฯ |

**อย่าสับสนสองหมุดนี้** — จุดน้ำเงินคือตำแหน่งของ*เครื่องที่เปิดเว็บอยู่* (มือถือในมือ)
ส่วน 🚌 คือตำแหน่งของ*กล่อง Pi บนรถ* คนละเครื่องกัน

กดที่หมุด 🚌 จะเห็นพิกัด ความเร็ว จำนวนดาวเทียม และ **แหล่งพิกัด** ที่บอกว่ากำลังดู
GPS จริง (`serial`/`gpsd`) หรือโหมดจำลอง (`route`/`fixed`) อยู่ — สำคัญตอนสาธิต
เพราะไม่งั้นแยกไม่ออกว่ารถวิ่งจริงหรือเป็นข้อมูลปลอม

ถ้า Pi เงียบไปเกิน **15 วินาที** หมุดจะเปลี่ยนเป็นสีเทาจาง หยุดกระเพื่อม และแถบสถานะขึ้น
"ขาดหาย N นาที" — หมุดยังค้างอยู่ตำแหน่งเดิมเพื่อบอกว่า "เห็นครั้งสุดท้ายตรงนี้"
ไม่ใช่หายไปเฉย ๆ จนไม่รู้ว่ารถอยู่ไหน

```bash
# ปิดการส่งตำแหน่ง (ถ้าไม่อยากให้หน้าเว็บเห็นรถ)
python3 device/pi_alert_client.py --serial --no-report

# ปิดชั้นหมุดฝั่งเว็บ (ไม่ได้เสียบอุปกรณ์ ไม่อยากเห็นป้าย "ออฟไลน์")
# http://localhost:8000/index.html?device=0
```

⚠️ **`POST /api/device/location` ไม่มีการยืนยันตัวตน** — ออกแบบมาให้ใช้ในวงแลนเดียวกับ Pi
เท่านั้น ถ้าจะเอาเซิร์ฟเวอร์ขึ้นอินเทอร์เน็ตสาธารณะ ต้องใส่ token ที่ endpoint นี้ก่อน
ไม่งั้นใครก็ยิงพิกัดปลอมเข้ามาแทนที่ตำแหน่งรถได้

เซิร์ฟเวอร์เก็บแค่ **ตำแหน่งล่าสุดจุดเดียวในหน่วยความจำ** ไม่มีประวัติย้อนหลังและไม่ลง
ฐานข้อมูล — รีสตาร์ตเซิร์ฟเวอร์แล้วหายไม่เป็นไร เพราะ Pi ส่งใหม่ภายใน 3 วินาทีอยู่แล้ว
ถ้าต่อไปอยากได้เส้นทางย้อนหลัง แก้ที่ `_device_location` ใน `api/server.py` จุดเดียว

### เสียงพูดบนอุปกรณ์ — 4 ชั้นเหมือนเว็บ

`speak()` ใน `pi_alert_client.py` ไล่ลงทีละชั้นจนกว่าจะมีชั้นไหนเล่นออก:

| ชั้น | แหล่งเสียง | ต้องมีเน็ต | หมายเหตุ |
|---|---|---|---|
| 0 | ไฟล์ Botnoi ใน `audio/` | ไม่ต้อง | เร็วสุด ไม่เสียพอยท์ — ใช้ตาราง `VOICE_CLIPS` ชุดเดียวกับ `js/tts.js` |
| 1 | Botnoi สดผ่าน `/api/tts` | ต้อง | ต้องตั้ง `BOTNOI_TOKEN` ฝั่งเซิร์ฟเวอร์ |
| 2 | Google `translate_tts` | ต้อง | ฟรี ไม่ต้องสมัคร |
| 3 | `espeak-ng` ในเครื่อง | ไม่ต้อง | เสียงแข็ง ใช้เป็นตัวสำรองสุดท้าย |

**ได้ยินแต่ buzzer ไม่พูด?** สาเหตุที่พบบ่อยที่สุดคือยังไม่ได้ลง `mpg123` ตรวจด้วย:

```bash
python3 device/pi_alert_client.py --checkvoice
```

บอกครบว่าไฟล์เสียงมีไหม ตัวเล่น mp3 มีไหม แล้วลองพูดตัวอย่างให้ฟังหนึ่งประโยค
ถ้าเล่นสำเร็จแต่ยังเงียบ แปลว่าเสียงไปออกผิดช่อง ใช้ `--audio-device plughw:2,0` เจาะจงการ์ดได้
(ดูเลขการ์ดจาก `aplay -l` · ใช้ `plughw:` ไม่ใช่ `hw:` เพื่อให้ ALSA แปลง sample rate ให้)

### ต่อลำโพงกับ Raspberry Pi 5 ด้วย MAX98357A (I2S)

**Pi 5 ไม่มีแจ็ค 3.5 มม.** และถ้าจอที่ต่อ HDMI ไม่มีลำโพง `aplay -l` จะเห็นแต่การ์ด
`vc4hdmi0/1` ซึ่งเปิดไม่ได้ (`Playback open error: -524`) จึงต้องเพิ่มทางออกเสียงเอง
โมดูล **MAX98357A** เป็น I2S DAC + แอมป์ Class-D ในตัว ต่อลำโพง 4-8Ω ได้ตรงๆ

การต่อสาย (เลข GPIO แบบ BCM / เลขขาจริงบนเฮดเดอร์ 40 พิน):

| ขาบนโมดูล | ต่อเข้า | ขาจริง |
|---|---|---|
| `Vin` | 5V | 2 หรือ 4 |
| `GND` | GND | 6 |
| `BCLK` | GPIO18 (PCM_CLK) | 12 |
| `LRC` | GPIO19 (PCM_FS) | 35 |
| `DIN` | GPIO21 (PCM_DOUT) | 40 |
| `SD` | ไม่ต่อ | — เปิดใช้งานตลอด |
| `GAIN` | ไม่ต่อ | — ใช้ค่า default 9dB |

**ไม่ชนกับ buzzer** ที่ใช้ GPIO13 (ขา 33) เพราะ I2S ใช้ GPIO18/19/21 คนละชุดกัน

เปิดใช้งานใน `/boot/firmware/config.txt` แล้ว `sudo reboot`:

```
dtoverlay=max98357a,no-sdmode
```

`no-sdmode` จำเป็นเมื่อไม่ได้ต่อขา `SD` — ไม่ใส่แล้วไดรเวอร์จะไปคุม GPIO4 ซึ่งไม่มีอะไรต่ออยู่
แล้วลำโพงจะเงียบ ถ้าโอเวอร์เลย์นี้ไม่ขึ้น ให้ลอง `dtoverlay=hifiberry-dac` แทน
(MAX98357A เป็น I2S DAC ธรรมดา ใช้ไดรเวอร์ตัวนั้นได้เหมือนกัน)

หลังรีบูตต้องเห็นการ์ดใหม่ใน `aplay -l` แล้วทดสอบ/รันด้วย:

```bash
aplay -l                                            # หาเลขการ์ด เช่น card 2
speaker-test -D plughw:2,0 -c 2 -t sine -f 440 -l 1  # ต้องได้ยินเสียงปี๊ด
python3 device/pi_alert_client.py --api http://localhost:8000 \
  --route data/mock_route.geojson --once --audio-device plughw:2,0
```

#### เร่งเสียงให้ดังขึ้น

MAX98357A **ไม่มีตัวคุมระดับเสียงในตัว** `amixer` จึงไม่มี control ให้เร่ง ปรับได้ 3 ทาง ใช้ร่วมกันได้ทั้งหมด

**ทางที่ 1 (ทำอยู่แล้ว) — เร่งตั้งแต่ตอนอัดที่ Botnoi** — เลือกระดับเสียง **300%** (ค่าสูงสุดที่ Botnoi ให้เลือก) ตอนสร้างไฟล์ที่ voice.botnoi.ai/tts แทนค่าเริ่มต้น 100%
ทำให้ตัวไฟล์ mp3 เองดังกว่าเดิมโดยเฉลี่ย **~5 dB** (วัดจริงด้วย `scripts/measure_audio_headroom.py`:
peak=1.000 rms=0.159 เทียบของเดิม rms~0.09) เพราะ Botnoi มีตัวบีบไดนามิกในตัวที่ดันช่วงเบา
ขึ้นแทนการคูณสัญญาณตรง ๆ — ทำแบบนี้ก่อนดีที่สุด เพราะไม่มีค่าใช้จ่ายด้านคุณภาพเสียงเพิ่ม
จากขั้นตอนถัดไป ไฟล์ทั้ง 12 ไฟล์ใน `audio/loud/` สร้างด้วยวิธีนี้

**ทางที่ 2 — `--volume` ที่ไคลเอนต์** ขยายสัญญาณเพิ่มอีกชั้นตอนเล่น (100 = ระดับเดิมของไฟล์)

```bash
python3 device/pi_alert_client.py --api http://localhost:8000 \
  --route data/mock_route.geojson --once --audio-device plughw:2,0 --volume 300
```

⚠️ **`--volume 300` นี้ใช้คู่กับไฟล์ใน `audio/loud/` ที่มาจาก Botnoi 300% แล้วเท่านั้น** เพราะไฟล์นั้น peak ชนเพดานดิจิทัลอยู่แล้ว (peak=1.000) การซ้อน `--volume 300` เพิ่มอีกชั้น
ทำให้พยางค์ที่ดังกว่าค่าเฉลี่ยมาก ๆ เกิด clipping จริง — ผู้ใช้ฟังเทียบบนลำโพงจริงแล้วยืนยันว่า
ยังฟังโอเค (2026-08-25) จึงตั้งเป็นค่าใน `systemd/mtec-alert-client.service` ไว้แล้ว **ถ้าเปลี่ยนไปใช้ไฟล์เสียงชุดใหม่ที่อัดจาก Botnoi ระดับอื่น (ไม่ใช่ 300%) ต้องวัด peak/rms**
**ใหม่ด้วย `measure_audio_headroom.py` แล้วทบทวนค่านี้ทันที** ไม่งั้นอาจดังเกินจนแตกหนักกว่านี้มาก

**ทางที่ 3 — ฮาร์ดแวร์** ขา `GAIN` เลือกอัตราขยายของแอมป์ ได้เสียงสะอาดกว่าเพราะขยายที่ภาคอนาล็อก

| ต่อขา `GAIN` เข้ากับ | อัตราขยาย |
|---|---|
| Vin ผ่านตัวต้านทาน 100kΩ | 3 dB |
| Vin โดยตรง | 6 dB |
| ปล่อยลอย (ค่าเริ่มต้น) | **9 dB** |
| GND โดยตรง | 12 dB |
| GND ผ่านตัวต้านทาน 100kΩ | 15 dB |

ต่อ `GAIN` เข้า GND (ขา 6 หรือ 9) ได้ 12 dB ดังขึ้นทันทีโดยไม่ต้องขยายด้วยซอฟต์แวร์
จึงไม่มีปัญหา clipping · ระวังว่าลำโพงที่ใช้รับได้ 2W ส่วนแอมป์จ่ายได้ราว 1.8W ที่ 8Ω
ถ้าตั้ง 15 dB แล้วเปิดดังสุดต่อเนื่องอาจเกินพิกัดลำโพงได้

ชั้น 0 match ข้อความ**แบบตรงตัว** ประโยคที่ระยะไม่ลงตัวที่ 500 เมตร (เช่น 400 หรือ 450)
จะไม่มีไฟล์ตรงแล้วตกไปชั้นถัดไปเอง — จงใจไม่บิดระยะให้เป็น 500 เพราะจะบอกระยะผิดกับคนขับ
เป็นพฤติกรรมเดียวกับเว็บ **ถ้าแก้ข้อความเตือนใน `riskrules.js`/`server.py` ต้องอัดไฟล์เสียงใหม่
และแก้ตาราง `VOICE_CLIPS` ทั้งใน `js/tts.js` และ `device/pi_alert_client.py` ให้ตรงกัน**

**Dynamic Alert** (`js/riskrules.js`): ข้อความเตือนประกอบจากกติกาตามเงื่อนไขจริงของจุด
เช่น ทางแยก/ทางโค้ง/จุดกลับรถ/ประวัติผู้เสียชีวิต/รถคันเดียวเสียหลักเป็นหลัก/ชนท้ายบ่อย
พร้อมคำแนะนำการขับขี่เฉพาะกรณี — ใช้ร่วมกันทั้งเสียงพูด แบนเนอร์ และ popup
ส่วน popup เพิ่ม**คำแนะนำเชิงวิศวกรรม**ตามรูปแบบปัญหา (Single-dominant → ไหล่ทาง/ราวกัน,
Multiple-dominant → สัญญาณไฟ/ช่องเลี้ยว)

## ตัวกรองจุดเสี่ยง (`js/filters.js`)

แผงมุมบนขวาของแผนที่ กรองได้ 3 แกน ใช้ร่วมกันได้:

| ตัวกรอง | ตัวเลือก |
|---|---|
| จังหวัด | ทุกจังหวัด หรือเลือก 1 ใน 6 จังหวัด (เติมอัตโนมัติจากข้อมูล) |
| ระดับความเสี่ยง | ติ๊กเลือกได้หลายระดับพร้อมกัน (สูง / ปานกลาง / ต่ำ) |
| ประเภทปัญหาหลัก | ทั้งหมด · Single-vehicle เด่น · Multiple-vehicle เด่น · ผสม |
| ดูจุดเสี่ยงรายอุบัติเหตุ | ติ๊กเปิดชั้นจุด 13,525 จุด (ดูอย่างเดียว ไม่มีผลกับการแจ้งเตือน) |

ตัวกรองมีผล**ทั้งหมุดบนแผนที่และการแจ้งเตือน** — `alert.js` อ่านจาก `RiskPoints.visible()`
เพื่อให้ "เห็นอะไรบนแผนที่ = ได้ยินเตือนเรื่องนั้น" ไม่สับสน จำนวนจุดที่แสดงอยู่
บอกไว้ท้ายแผง (เช่น "แสดง 16 จาก 456 วง") กดหัวแผงเพื่อย่อ/ขยาย และมีปุ่มล้างตัวกรอง

### หมุดคลัสเตอร์กับแนวถนน

หมุดของแต่ละคลัสเตอร์คือ medoid = พิกัดอุบัติเหตุจริงจากข้อมูลกรมทางหลวง ซึ่งมีความ
คลาดเคลื่อน GPS ราว 0-15 เมตร พอซูมเข้าใกล้จะเห็นหมุดเยื้องออกจากเส้นถนนเล็กน้อย

แก้ด้วย `py scripts/snap_markers_to_road.py` — ยิง OSRM หาจุดบนแนวถนนที่ใกล้ที่สุด
แล้วย้ายหมุดไปที่นั่น (รอบล่าสุด: ย้ายครบ 456 จุด · ระยะกลาง 3.9 ม. · มากสุด 29.6 ม.)

- เก็บพิกัดเดิมไว้ในฟิลด์ `medoid_raw` ทุกจุด ย้อนกลับได้ ตรวจสอบได้
- ระยะที่ย้ายบันทึกไว้ใน `snap_distance_m`
- ถ้าถนนใกล้สุดห่างเกิน 30 ม. ถือว่าจับผิดเส้น จะไม่ย้าย
- **ต้องรันใหม่ทุกครั้งหลัง `build_risk_points.py`** เพราะ build เขียนทับด้วยพิกัดดิบ
- เป็นการปรับเพื่อการแสดงผลเท่านั้น ระยะไม่กี่เมตรเล็กกว่ารัศมีเตือน 500 ม. มาก
  ระดับความเสี่ยง/SI/EPDO ไม่เปลี่ยน (ตรวจแล้ว ต่ำ 319 · ปานกลาง 113 · สูง 24 เท่าเดิม)

ทดสอบรวมทั้งระบบ: เปิด `http://localhost:8123/?mock=1` — ระบบจะวาดเส้นทางจำลอง
แล้วขับตามถนนจริง (แยกสาครเกษม - คลองมะเดื่อ จ.สมุทรสาคร ~6.2 กม. ทิศทางเดียวไม่สวนเลน)
ซึ่งชุดข้อมูล 3 ปีมีคลัสเตอร์ตามแนวเส้นทาง 7 วงในรัศมีเตือน **ครบทั้งสามระดับ**
(ต่ำ zone_431/432/439 · ปานกลาง zone_440/441/453 · สูง zone_455)
ต้องได้ยินเสียงเตือน**หนึ่งครั้งต่อจุด**ตอนเข้าเขต 500 ม.
และไม่เตือนจุดเดิมซ้ำจนกว่าจะออกนอกเขตแล้วกลับเข้ามาใหม่

ขับด้วยความเร็วสมจริง 80 กม./ชม. (มีช่วงออกตัวและชะลอก่อนถึงปลายทาง) ใช้เวลาราว 4 นาทีครึ่ง
ปรับได้ด้วย `?mock=1&kmh=120` เพื่อดูให้จบไว หรือ `?mock=1&kmh=40` เพื่อดูจังหวะเตือนแบบช้าๆ

### ทดสอบภาคสนามจริงในอุทยานวิทยาศาสตร์ฯ (สวทช. ปทุมธานี)

`test-nstda.html` = สนามทดสอบ GPS จริงบนถนนวงรอบอุทยานวิทยาศาสตร์ฯ 1.4 กม.
มีจุดเสี่ยง**สมมติ** 8 จุด (ต่ำ 4 · ปานกลาง 3 · สูง 1) วางบน node ถนนจริง ขับรอบเดียวได้ครบ
เริ่มที่ถนนฝั่งตะวันออกหน้า Multi Purpose Building แล้ววนตามทิศทาง one-way จริง

```bash
python scripts/build_nstda_test_site.py      # สร้าง/สร้างใหม่ชุดข้อมูลสนามทดสอบ
# ซ้อมในห้อง: http://localhost:8123/test-nstda.html?mock=1&kmh=30
# หน้างาน:    http://localhost:8123/test-nstda.html   (ต้องเปิดผ่าน https หรือ localhost)
```

หน้านี้ใช้โค้ดชุดเดียวกับ `index.html` ทุกบรรทัด ต่างแค่ชุดข้อมูล + รัศมีเตือน
ที่ย่อเหลือ 60/80 ม. (พื้นที่ทั้งอุทยานฯ เล็กกว่ารัศมี 500 ม. และจุดบนถนนฝั่งตะวันตก
ห่างกันเพียง 71-125 ม.) ลองรัศมีอื่นสดหน้างานได้ด้วย `?alert=40&exit=60`
**ตัวเลขอุบัติเหตุในชุดนี้เป็นข้อมูลสมมติ ห้ามนำไปรายงานปนกับชุด MOT**
